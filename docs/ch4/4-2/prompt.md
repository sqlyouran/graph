【当前状态】
- Spring Boot + Spring AI 已能通过 ChatClient 调用真实大模型
- 前端已经能提交旅行问题并展示一段 Markdown 行程
- 当前模型还没有旅行工具，航班、酒店、景点、天气可能依赖模型记忆或猜测
- 当前还没有业务多轮 Loop，也没有 C1-C7 量化验收

【本节目标】
让模型能主动查询四类固定旅行事实，再基于工具返回完成行程；同时补齐前端演示所需输入，让页面能够明确提供出发地、目的地、出发日期、天数、预算和酒店限价，从而稳定触发四类工具。工具查不到时必须诚实说明暂无数据，不能补造事实。

【事实数据与数据契约】
1. 在 src/main/resources/facts/ 下新增 flights.json、hotels.json、attractions.json、weather.json 四份小型课程快照，至少覆盖杭州及现有演示城市
2. 数据字段使用程序可读取的稳定类型：
   - 航班：航班号、出发地、目的地、起飞时间、到达时间、价格
   - 酒店：名称、城市、区域、每晚价格、评分
   - 景点：名称、城市、区域、门票、开放时间、闭馆日、建议游玩时长
   - 天气：城市、日期、天气、最低/最高温度、降水概率
3. 金额使用数值类型，日期和时间使用明确格式；不要把价格、日期或开放时间塞进自然语言说明
4. 新增 TravelDataService，从 classpath 加载并查询快照；启动时校验文件可解析和关键字段完整，损坏时直接报清楚的配置错误
5. 城市查询统一处理前后空格和“杭州市/浙江杭州”这类课程中明确支持的常见写法；不能因为做归一化就推导快照之外的新城市

【四个模型工具】
新增 TravelTools，并使用 Spring AI 的 @Tool / @ToolParam 暴露以下能力。名称可以遵循项目现有约定，但职责不能合并：
1. searchFlights：按出发地和目的地查询航班事实
2. searchHotels：按目的地查询酒店；如保留最高每晚价格参数，约定 0 表示不限价
3. searchAttractions：按目的地查询景点、门票、开放时间和闭馆日
4. queryWeather：按目的地和日期查询天气快照

每个工具描述必须写清：什么时候调用、参数格式和示例、返回哪些字段、覆盖范围外返回空列表。模型只能看到工具名称、描述、参数和返回值，因此描述不能只写“查酒店”“查天气”。

【查不到时的行为】
- 没有匹配事实时返回空列表，不抛出“用别的值再试”的业务异常
- 不返回全国平均价、默认酒店、默认景点、预设行程或任何占位事实
- 不把模型常识补充的数据标成工具结果

【接入 ChatClient】
1. 在现有模型调用上注册 TravelTools，不新增第二套聊天入口
2. 增加系统事实纪律：航班、酒店、景点和天气的价格与时间必须来自工具；工具为空时明确回复“该城市/日期暂无数据”；引用价格保持工具原值
3. 行程仍按天输出，并在末行保留固定格式“预计总花费 XXXX 元”，供第四章的基础契约检查使用
4. 每次工具执行记录一条不含密钥的日志，至少能看到工具名、查询条件和返回条数，方便课堂验证模型是否真的取了事实

【明确不做】
- 不接真实订票、地图或天气 API，不引入数据库、缓存或消息队列
- 不实现业务外层多轮 Loop，不实现 C1-C7、ConstraintChecker 或预算核算
- 不引入 Token 预算、总超时、无进展检测、记忆、SSE 或 Graph
- 模型调用失败时不得静默回退到内置行程
