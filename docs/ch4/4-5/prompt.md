【本节目标】
实现“生成候选 → 基础检查 → 记录问题 → 带反馈重新生成”的外层 Loop，并且只有两个业务出口：基础契约通过，或者达到最大轮次。无论从哪个出口结束，都返回当前最好版本和真实原因。

【任务输入与状态】
1. 将前端输入整理为结构化 PlanRequest，至少包含出发地、目的地、开始日期、天数、预算、偏好和 maxRounds；预算本章只保留，不做真假核算
2. 为每轮保留不可变或可回放的状态快照，至少包含：原始需求、当前 Markdown 行程、基础检查结果、反馈问题清单、当前轮次、过程事件
3. 不要覆盖后只留下最后一版；测试必须能读取第 1 轮和第 2 轮分别发生了什么

【生成职责】
1. 抽出可替换的 PlanGenerator 或沿用项目已有的生成接口；正式实现继续使用当前真实 ChatClient 和 TravelTools
2. 第 1 轮根据原始需求生成完整行程
3. 后续轮次必须同时带入原始需求、上一版完整行程、上一轮全部问题，并明确要求“保留已合格部分，返回一份完整修订版”
4. 宿主的一轮只允许一次候选生成；不要在生成器内部增加三次重试或静默回退
5. 模型调用异常要返回清楚的失败结果，不得返回内置行程伪装成功

【本章基础检查】
新增 BasicContractReview 或遵循项目现有命名的等价组件，只检查 Markdown 是否满足基础交付格式：
- 请求的第 1 天到第 N 天是否都有安排
- 是否包含住宿和景点等基础行程内容
- 末尾是否存在固定格式“预计总花费 XXXX 元”

检查结果至少包含 passed 和 problems；每个问题必须能直接进入下一轮反馈。不要比较模型声明总价与预算，不要重新计算机票、酒店或门票，不要检查闭馆日、营业时间、路线和节奏，这些留到第五章。

【Loop 主干与两个出口】
1. TravelPlanningEngine 使用清楚的串行 while/for 循环，不引入 Graph、状态机框架或递归
2. 每轮顺序固定为：开始一轮 → 生成候选 → 基础检查 → 保存状态和事件 → 通过则返回
3. 未通过且还有轮次时，将全部 problems 作为反馈进入下一轮
4. 基础检查通过返回 COMPLETED 或项目现有的等价状态
5. 达到 maxRounds 返回 MAX_ROUNDS / STOPPED 等诚实状态，同时保留当前最好版本和未解决问题
6. 轮次判断由宿主程序负责，不相信模型在文本里自报“完成”

【事件与页面】
1. 提供轻量 EventSink 或复用现有事件出口；记录轮次开始、工具调用、生成完成、检查完成、反馈进入下一轮和最终结束
2. 本章事件先随结果返回或写入当前页面状态，不实现 SSE
3. 事件记录失败不能中断工具调用或 Loop 主流程
4. 前端提交结构化 PlanRequest；右侧按轮次显示工具、检查、反馈和最终状态
5. 基础契约通过显示绿色“规划完成”；达到上限显示橙色“已达最大轮次”，并继续展示当前最好行程
