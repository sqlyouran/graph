# 7-4 第三轮补账 Prompt（假还的账与没动的账）

接着上一轮做。门搬出来了、枚举挂上方法了、确认不重识别了——这三笔记账。
但有两笔没还：测试一个没写，相对量的澄清全是死代码。这轮就还这两笔，
外加顺手清三处补丁痕。现有 86 个测试全绿，一个都不许坏。
契约照旧冻结：九个动作的枚举值、/chat 的请求响应形状、PlanningChatDecision 语义、
INTENT_RECOGNIZED 事件、RevisionPolicy 不许绕——一行都不要动。

一、测试。这是上一轮唯一没动的账，这轮必须交。
1. 九个动作各至少一条命中测试；
2. 失败路径一组：模型返回不存在的枚举、槽位类型不对、缺必需槽位，三条分别
   落到 UNKNOWN，且不许抛异常；
3. 最硬的一条：证明 UNKNOWN、澄清、ASK_QUESTION 这三条路径永远碰不到
   planningEngine.plan——上一轮"回滚零模型调用"的证法可以照抄；
4. 确认门一组：REVISE_BUDGET 和 CANCEL 确认前不许执行、确认后执行；
   ROLLBACK 不用确认直接执行。
注意第 2 条和第 3 条的边界要跟着下面第二条一起改，改完再写测试。

二、缺槽位归门管，不归识别器管。
现在识别器把"没听懂"和"听懂了但没说全"混成一件事：缺了必需槽位直接判
UNKNOWN，于是门里那六条澄清话术一条都用不上，用户说"酒店太贵"还是得到
"我没能确定你的意思"。分工改成：识别器只做类型校验（数字得是正整数、
列表得是字符串），槽位缺不缺它不管；缺槽位的 REVISE_* 活着送到门，由门
走已经写好的那六条澄清。识别器回答"用户想干什么"，门回答"接下来走哪条路"，
缺槽位是后者的事。改完之后，"酒店太贵"必须得到"你希望把酒店每晚限价调整
到多少"这类具体的话，不许再落到通用听不懂。

三、枚举不许撒谎。
PlanningIntentAction 上 NEW_SESSION 现在标着"不需要确认"，但控制器对它的
实际行为是"建议新会话"、根本不执行——枚举说的和系统做的不一致。改成枚举
如实表达这个动作的性质，门根据枚举决定走"建议"还是"执行"。改完后这条
分支的行为不许变：后端依然不许自动开新会话。

四、清三处补丁痕。
1. chat 方法里确认分支有两个连续的 if 都在处理 pendingIntent，第一个赋值
   完第二个又重建一遍——留一个，把重复的删掉；
2. 上一条删干净之后，门里那句"两次说法不一致就回澄清"的比对就变成永远
   成立的死代码，一起删；
3. PlanningIntentValidator 和 facade 里的 unknown() 现在没人用了，删掉。
