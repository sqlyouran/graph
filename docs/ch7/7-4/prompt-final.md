# 7-4 意图识别完整 Prompt
接着上一轮做。现在用户能取消、能续修、能回滚，但都得靠表单填结构化字段。
这一轮让它能听懂人话。现有测试全绿，一个都不许坏。

先说清楚要做成什么样。用户会说这类话：
  "太贵了" / "酒店太贵" / "第二天太赶" / "能不能住民宿" / "算了不弄了" /
  "还是上一版好" / "回滚到 2" / "改去南京吧" / "雷峰塔几点关门"
系统要把它们变成结构化动作，然后走上一轮已经建好的那条链路。

一、动作集合定死九个，别自己加：
REVISE_BUDGET / REVISE_HOTEL_PRICE / ADD_MUST_VISIT / ADJUST_PACE /
CANCEL / ROLLBACK / NEW_SESSION / ASK_QUESTION / UNKNOWN。
为什么定死：每个动作都要能落到 RevisionPolicy 白名单里的字段上，落不上的动作
识别得再准也没用，用户只会看到一次莫名的失败。UNKNOWN 和 ASK_QUESTION 必须是
枚举里的合法值，不是异常也不是 null。

二、做成级联的两层，别只用模型。
第一层规则：取消 / 停（含裸字"停"）/ 回滚 / 还是上一版 —— 直接命中出动作，不调模型。
理由是这些说法固定，而且用户按取消的时候在着急，让他等一次模型调用没道理。
规则层前面再加两道相对量短路："酒店太贵"返回**缺槽位的** REVISE_HOTEL_PRICE，
"太贵了"返回**缺槽位的** REVISE_BUDGET。判据不是"用户说了'太贵'"，是"用户的话里
没有数字，而动作需要数字"——按这条查一遍九个动作，落得上的都不许默默转成通用
听不懂。模型可以提议，不能替用户决定花多少钱。
第二层才是模型，走结构化输出，给它 JSON schema。

三、模型的输出必须校验，别信它，但校验只管类型。
action 不在九个里面 → 当 UNKNOWN 处理，不要抛异常：解析枚举必须用带兜底的写法
（valueOf 外面包 catch 或等价物），识别失败是正常分支不是系统故障。
slots 只做类型校验：budget 正整数、mustVisit 字符串列表，类型不对当 UNKNOWN。
**槽位缺不缺不归识别器管**——识别器回答"用户想干什么"，门回答"接下来走哪条路"，
缺槽位是后者的事。缺槽位的 REVISE_* 必须活着送到门。

四、门单独成类（PlanningIntentGate），不许挤在控制器里。
控制器的活是收 HTTP 请求，门的活是决定这句话走哪条路，两件事分开——不然以后排障
分不清是"门开错了"还是"路走错了"。门里的判断顺序冻结：没听懂 → 六条缺槽位澄清
（预算 / 酒店限价 / 必去景点 / 节奏 / 目的地 / 问句，各给具体的问话，不许用通用
听不懂）→ 要确认 → 才派发。这个顺序就是这一层的全部设计：每个提前退出都在省钱，
所有退路都排在花钱那一步前面。验收："酒店太贵"必须得到"你希望把酒店每晚限价调整
到多少"这类具体的话。

五、动作的性质挂回枚举上，枚举不许撒谎。
枚举自己回答三个问题：requiresSlots()、requiresConfirmation()、dispatchesOperation()。
门和控制器只问枚举，不做枚举；以后加第十个动作，在枚举里回答这三个问题就行，
链路一行不用改。NEW_SESSION 的实际行为是"建议新会话"、根本不执行，枚举就必须
如实表达这个性质；控制器的"建议新会话"分支由 dispatchesOperation() 推出来，不是
凭空冒出来的 if。改完后行为不许变：后端依然不许自动开新会话。

六、确认时不许重新识别。
用户带 confirmed=true 回来，是对上一回显的那份理解点头，不是让系统再听一遍。
确认时直接取会话上挂着的 pendingIntent 用，只留一处赋值，不许有重建第二遍的
重复代码；pending 是空的就回澄清。重跑识别会白烧一次模型调用，还引入"两次识别
结果不一致"的风险。

七、要不要先确认，按这条判据：动作可逆且零成本的直接执行（ROLLBACK 就是切指针，
切错还能切回来）；会花钱或不可逆的一律先回显确认（REVISE_* 会启动三轮 Loop，
CANCEL 会终止正在跑的规划）。回显不要写成"确定吗"，要把理解讲出来：
  "我理解成：把总预算从 2600 提到 3000，其他不变。这就开始改？"
因为系统没法知道自己听错了，用户一眼就知道。

八、识别结果必须再过 RevisionPolicy，不许绕过，也不许把校验逻辑抄一份到识别器里。
识别器管"用户想干什么"，是概率问题，允许错；RevisionPolicy 管"这事允不允许"，
是规则问题，不许错。合在一起写，以后出问题你分不清是听错了还是越权了。
取消 / 续修 / 回滚一律调上一节现成的链路，一个都不许重新实现。

九、事件补一种 INTENT_RECOGNIZED，推 action、槽位、人话回显；别推置信度原始分数，
用户看 0.72 没有意义。白名单还是 SsePlanningEventSink 那个白名单，新类型记得加进去。

十、入口加一个新端点：POST /api/plan/{id}/chat，body 就 utterance 和 confirmed 两个字段。
响应把三件事说清楚：理解成了什么（action + 槽位 + echo）、门的决定（直接执行 /
等确认 / 再问一句 / 建议新会话）、问句或答案文本。pending 的理解放在会话上，服务端
不许自己维护多轮对话历史。规则层命中 CANCEL，确认门生效后调上一节现成的取消链路
——规则层只是识别得快，不免确认；ROLLBACK 没带版本就默认当前版本的前一版，没有
前一版就问一句；NEW_SESSION 在响应里带上用户说的新目的地，门的决定是"建议新会话"，
让前端走新行程流程；ASK_QUESTION 用一次普通模型调用回答，不进规划 Loop。

十一、不要做的：多轮对话状态机（一次只处理一句，需要澄清就回一个问题）、自由文本
直接改行程（还是只能改白名单字段）、语音输入、把识别结果缓存起来复用、留下没人用的
校验类和死代码比对。

十二、测试，一次交全，四组：
1. 九个动作各至少一条命中测试；相对量两条要断言"返回的是缺槽位的 REVISE_*，不是
   UNKNOWN"；规则层命中的用例要断言零模型调用。
2. 失败路径三条：识别结果是不存在的枚举、槽位类型不对、缺必需槽位——前两条落到
   UNKNOWN 且全程不抛异常，第三条活着送到门、由门澄清。
3. 最硬的一条：证明 UNKNOWN、澄清、ASK_QUESTION 这三条路径从 /chat 端点走到底，
   一次都碰不到 planningEngine.plan。证法照抄 PlanningRollbackTests 里"回滚零调用"
   那条：引擎用 mock(TravelPlanningEngine.class)，断言 verifyNoInteractions(engine)；
   识别器用一个假的 PlanningIntentRecognizer 实现，分别返回 UNKNOWN、缺槽位的
   REVISE_BUDGET、ASK_QUESTION 三种意图；再断言会话事件里不出现 GENERATION_STARTED。
   注意："门说不"不等于"引擎没被碰"，门和引擎中间还隔着控制器整段派发逻辑，这段
   必须被测试盖住，才算证明成立。不许用门层单测顶替这条端点级证明。
4. 确认门一组：REVISE_BUDGET 和 CANCEL 确认前不许执行、确认后执行；ROLLBACK 不用
   确认直接执行。
