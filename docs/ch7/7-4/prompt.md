# 7-4 补账 Prompt（意图识别第一版的欠账）

接着意图识别这一版做。功能方向对了，但有三笔欠账要还。现有 86 个测试全绿，一个都不许坏。
已经定下来的契约不许改：九个动作的枚举值、POST /api/plan/{id}/chat 的请求响应形状、
PlanningChatDecision 的语义、INTENT_RECOGNIZED 事件、"识别结果必须过 RevisionPolicy"——
这些一行都不要动，这轮只动内部结构。

一、把门从控制器里搬出来，单独成类（比如 PlanningIntentGate）。
现在识别之后的判断挤在 PlanController 的 chat 方法里：哪些动作先短路、哪些要确认、
哪些要澄清，全靠 if-else 的顺序表达。控制器的活是收 HTTP 请求，门的活是决定这句话
走哪条路，两件事必须分开——不然以后排障分不清是"门开错了"还是"路走错了"。
搬出来之后，门里的判断顺序不许变：没听懂或要澄清 → 槽位不全 → 要确认 → 才派发。
这个顺序就是这一层的全部设计：每个提前退出都在省钱，所有退路都排在花钱那一步前面。

二、动作的性质挂回枚举上。
PlanningIntentAction 现在是个裸枚举，"哪个动作要确认"靠控制器里先排掉 ROLLBACK、
剩下全要确认的负向写法实现。加第十个动作就得回来改控制器——这叫性质长在了外面。
正确做法：枚举自己回答两个问题——需不需要槽位、需不需要确认。门只问枚举，不做枚举。
以后加动作，只需要在枚举里回答这两个问题，门和控制器一行不用改。

三、确认时不许重新识别。
用户带 confirmed=true 回来，是对上一回显的那份理解点头，不是让系统再听一遍。
现在每确认一次就重跑一遍识别，模型层白烧一次调用，还引入"两次识别结果不一致"的风险。
确认时直接取会话上挂着的 pendingIntent 用；如果 pending 是空的或者对不上，回澄清。

四、相对量别只兜预算。
用户说"酒店太贵"，现在收到的是通用的"我没能确定你的意思"——这跟没说一样。
判据不是"用户说了'太贵'"，是"用户的话里没有数字，而动作需要数字"。按这条查一遍九个
动作，凡是能落到这条上的，要么问一句，要么给两三个候选让用户选，不许默默转成通用
听不懂。模型可以提议，不能替用户决定花多少钱——这条上一轮就说过，这次要落全。

五、规则层把裸字"停"加进去。
现在"停了""停止"命中，单打一个"停"字反而落到模型层。取消和停止的话术高度固定，
这正是规则层该短路掉的话。

六、测试欠账，这轮必须还。
1. 九个动作各至少一条命中测试；
2. 失败路径一组：识别返回不存在的枚举、槽位类型不对、缺必需槽位，三条分别落到
   UNKNOWN，且不许抛异常；
3. 最硬的一条：证明 UNKNOWN、澄清、ASK_QUESTION 这三条路径永远碰不到
   planningEngine.plan——怎么证明你来说，上一轮"回滚零模型调用"的证法可以照抄；
4. 确认门一组：REVISE_BUDGET 和 CANCEL 在确认前都不许执行、确认后执行；
   ROLLBACK 不用确认，直接执行。
