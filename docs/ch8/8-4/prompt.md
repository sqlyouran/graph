# Prompt T：自动化评测

我们这一章做了两块新能力：上下文组装和记忆管理。要建一套自动化评测来持续验证它们。要验的维度和对应的检查逻辑一共八条。

第一条，预算丢弃顺序：构造一个 token 预算很紧的场景，检查组装结果里画像区被移除了，约束区和详细历史还在。再构造一个更紧的场景，检查详细历史是否降级成最小摘要，约束区仍然保留。丢弃顺序是画像先丢，然后是详细历史，约束区和指令区永远不丢弃。

第二条，丢弃可追溯：上面那个被移除或降级的场景里，返回结果的 droppedSections 列表必须包含区段名称和原因，比如"profile: 剩余预算不足"。如果组装器做了取舍却没记录，调试时就是黑箱。

第三条，偏好晋升：给一个"连续三次把酒店换成民宿"的修改序列，检查第三次之后是否出现确认候选；模拟用户点击确认后，画像里才出现住宿偏好。再给一个只改了两次的序列，检查既没有确认候选，也没有这条画像。两个都要过。

第四条，遗忘衰减：先建立并确认一条"偏好民宿"，然后记录一次"换成连锁酒店"的相反修改，检查旧偏好是否立即移除；再把时钟往后拨，检查长期未使用时置信度会下降。

第五条，条件偏好：画像里有"带孩子不爬山"，请求里说"这次带孩子"，方案不含登山；请求里没提孩子，方案可以有登山。

第六条，显式覆盖：画像里有"偏好民宿"，请求里说"这次试试酒店"，本次方案不含民宿；下一次请求不说，民宿偏好恢复注入。

第七条，跨用户隔离：同时给两个用户跑规划，检查各自的 prompt 里不包含对方的偏好文本。

第八条，个性化命中率：给定画像和请求，跑一次规划，检查输出方案是否体现了注入的偏好。这一条用 AI 来判——给它偏好描述和方案全文，让它回答"方案是否体现了这条偏好"，是或否。把 judge 抽成接口，课堂回放默认使用不联网的可重复实现，接真实模型时再替换实现。

输出要求方面：每个维度跑完后输出通过率；第八维用 judge 模式，同一条跑三次取多数票，消除 judge 自身的方差；最终汇总成一份报告，按维度列出通过率和失败用例。评测脚本里每个画像用独立的 userId，跑完清理本次生成的 profiles 目录——残留偏好会污染下一轮评测，这个坑要在脚本层堵住。
